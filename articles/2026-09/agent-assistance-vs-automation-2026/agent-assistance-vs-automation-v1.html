Agent · Assistance · Automation

Claude Code之后
协作与自动化不是同一场比赛

从DHH与Jev创始人的两场访谈，看Agent软件的双重演进

一个观点把人推向创造中心，另一个观点要把人从运行环路中移走。它们并不真正矛盾：前者回答软件如何被创造，后者回答软件如何被长期执行。

深度解读与分析｜2026年9月

在Lex Fridman的访谈中，DHH兴奋地描述自己如何同时运行多个编码Agent，用自然语言编程，为一个人的需求快速做出软件。他的结论是：Agent没有终结编程，而是把程序员从大量实现工作中释放出来，让人重新回到创造、判断和审美。[1]

几乎在同一时期，TypeSafe AI创始人Diogo Almeida却提出一个更尖锐的判断：Claude Code并不代表下一个时代，它与ChatGPT仍属于同一个“人机协作时代”。真正的下一站应当是无需人持续盯守、能够在后台稳定运行的自主自动化。[2]

一个人说，Agent让人与机器的协作进入黄金时代；另一个人说，下一代系统恰恰要把人从环路中拿掉。两种观点看似正面冲突，却分别抓住了AI软件的两个不同问题：创造过程需要什么，生产运行又需要什么。

一、真正的矛盾，不是“人留不留下”

如果只截取最响亮的句子，两场访谈几乎互相否定。DHH说自然语言正在成为新的编程语言，Claude Code的多Agent体验让他比过去更愿意创造；Almeida则把Claude Code与ChatGPT放在同一时代，认为它们都没有跨过从辅助到自动化的边界。

但Almeida并没有否认Claude Code的价值。他在演讲中明确说自己喜欢并会继续使用Claude Code。他反对的不是编程Agent，而是把“编程Agent越来越好用”直接等同于“企业流程已经可以无人值守”。[2]

DHH也没有声称多个Agent能够独立经营一套关键业务。他描述的工作流中，人始终在场：提出目标、分配任务、接受通知、处理冲突、审查结果并决定是否合并。Agent拥有更大的执行空间，但产品方向和最终责任仍然在人。

因此，两人的差异不能用“乐观与悲观”概括。更准确的说法是：

DHH讨论的是如何降低创造软件的成本；Almeida讨论的是如何降低软件持续作出语义判断的成本。

二、DHH的答案：让人留在创造环路中

DHH的变化来自连续数月的真实使用。他让多个Agent在不同机器上并行工作，用Claude Code的Agent视图管理线程，也会使用其他模型和工具。他提到，自己现在大量通过英语而不是传统编程语言表达意图，但仍然阅读代码、观察行为并作出决定。[1]

这套工作方式的核心并不是“模型替程序员完成更多代码”，而是人的注意力发生上移：

从实现转向问题

程序员不再需要亲自完成所有机械步骤，可以把更多时间用于决定什么值得构建。

从串行转向并行

分析、实现、测试和审查可以同时推进，人负责保持这些线程服务于同一个产品方向。

从通用产品转向个人软件

Omawrite这样的案例表明，当第一版成本降低，只服务一个人或小团队的软件也可能成立。

从代码稀缺转向判断稀缺

生成的补丁越来越多以后，边界、品味、可维护性和最终责任成为新的瓶颈。

在这条路线中，模型最有价值的地方恰恰是开放性。自然语言可以表达未完全形式化的愿望，生成式模型可以提出实现、解释代码、修改界面，也可以在需求变化时快速重来。它的优势来自自由度，而不是消除自由度。

这也决定了人的位置。探索阶段的问题没有唯一正确答案，产品品味无法完全写成单元测试，需求甚至会在看到原型以后才变得清楚。此时把人拿出环路，不是自动化升级，而是过早冻结问题。

三、Jev的答案：让人退出稳定运行的环路

Almeida从另一个痛点出发。企业软件中存在大量高频、边界相对明确、但传统规则难以理解非结构化输入的微小判断：工单该路由到哪里，一封邮件是否表达取消意图，一个事件应落在哪个风险等级，一组对象应如何排序。

把这些任务交给通用大模型，常见做法是要求它生成JSON，再在外部增加解析、验证、重试和回退。模型本来输出面向人的字符串，软件却要把字符串重新翻译成可以执行的结构。Almeida认为，这种接口从根上错配了。

Jev因此放弃开放式文本生成，提供三类预先定义的决策原语：Choice从有限选项中选择，Score按照量表评分，Noul估计某个陈述为真的程度。状态和类型化问题进入，结构化结果、概率与置信信息出来；多个原子问题可以并行计算，再由普通代码组合。[3]

这条路线不追求让模型模拟一个“全能数字员工”，而是把复杂业务拆成许多小而明确的语义判断。模型给出概率，代码决定阈值：高置信度自动通过，中间区间进入规则复核，低置信度或高风险样本交给人。

TypeSafe把这种训练目标称为RLCD，即面向校准决策的强化学习。它与面向人类偏好的RLHF、面向可验证答案的RLVR强调不同的优化对象。这里最重要的不是缩写本身，而是Almeida提出的工程原则：自动化模型不只要给答案，还要让自己的置信度具有统计意义。[4]

四、真正的分野：对象、目标与失败方式

把两场访谈放在同一张表里，可以看到它们并不是对同一个产品作相反评价，而是在描述两种不同的软件生产关系。

比较维度DHH的人机协作Almeida的自主自动化
核心问题一个人如何创造更多、更贴合意图的软件软件如何长期处理真实业务而无需持续监督
主要任务探索、设计、编码、调试、个性化工具分类、路由、筛选、评分、风险分层
输出消费者人类程序员、产品创造者程序、工作流、后台服务
理想接口自然语言、代码、解释与可追问对话强类型结果、概率、置信度与固定契约
人的角色持续定义、判断、审查与整合事先设计、设阈值，异常时介入
主要失败方向错误、复杂度失控、生成过多无用代码错误决策被规模化执行、概率失准、数据漂移
成功标准更快学习、更好作品、更高创造密度长期可靠、成本可控、错误率和升级率可测

DHH需要模型保留一定开放性，因为创造本身要穿过不确定性；Almeida需要模型放弃部分开放性，因为生产系统必须把可发生的状态限制在契约之内。一个在扩大可能空间，另一个在收缩运行空间。

这也解释了为什么自然语言在一个场景中是优势，在另一个场景中却成为成本。对人而言，语言可以容纳模糊意图和新概念；对程序而言，任意字符串意味着解析、验证、重试和不可穷举的失败状态。

五、任务应该放在哪一条路上

判断一项工作适合人机协作还是自动化，不能只看它“难不难”。更有用的两个维度是：任务能否事先形式化，以及错误后果是否容易逆转。

“高频、低风险、可分解”是自动化最自然的起点；“低频、高歧义、结果决定方向”更适合让Agent辅助人。即使任务边界清楚，只要错误不可逆，也不应仅凭一个置信度就完全放行，还需要权限、双重验证、速率限制和人工升级。

反过来，人留在环路中也不等于逐条手工审核。成熟系统会让人负责制定政策、选择损失函数、设定阈值和处理异常，而不是永远坐在屏幕前确认每一次调用。

六、Jev解决了什么，又没有解决什么

Jev提出了一个值得重视的接口创新：如果任务最终只需要有限选择、评分或真假概率，就没有必要先让模型写一段漂亮文字，再费力把文字解析回程序状态。类型化输出可以直接消除格式错误这一整类失败，也能显著降低延迟和输出成本。

但“类型安全”不能被误读成“决策一定正确”。TypeSafe官方材料所说的“不会幻觉”，主要指模型不生成任意字符串、不会返回模式之外的类型；它仍然可能在允许的选项里做出错误选择。官方文档也明确要求开发者针对自己的任务评估准确率和置信度。[3]

类型正确 ≠ 语义正确

返回值一定属于A、B、C，并不意味着选中的B就是业务上的正确答案。

总体校准 ≠ 个体无风险

一批80%置信度样本长期正确率接近80%，仍意味着其中约五分之一可能错误。

发布评测 ≠ 外部定论

193.6倍速度和444.6倍成本优势来自公司设计的工作流评测；官方也说明这些属于现实收益的高端区间。

历史校准 ≠ 永久校准

业务数据、语言和攻击方式变化后，原有阈值可能失效，需要持续监控与重新评估。

事实口径：TypeSafe公布的输入价格、延迟和性能优势属于其早期产品及自有评测结果。官方博客同时披露了服务位置、样本设计、参考模型和潜在偏差等限制；因此这些数据适合说明技术方向，不宜直接外推为所有生产任务的普遍结果。[4]

这并不削弱Jev的意义，反而把它放回了正确位置：它不是“不会犯错的模型”，而是一种让错误空间更容易被定义、测量和治理的模型接口。

七、统一框架：创造环路、运行环路与治理环路

真正完整的Agent软件，不会在Claude Code和Jev之间二选一。更合理的架构，是让不同模型和接口进入不同平面。

一个退款自动化系统可以由人和编码Agent共同设计。团队先用生成式模型理解邮件、发现例外、建立评测集；当模式稳定以后，把“取消意图”“欺诈风险”“客户等级”等拆成类型化判断；工作流按照概率与金额设置阈值，低风险小额退款自动执行，高风险或置信不足的请求升级给人。

此时，Claude Code并没有被Jev淘汰。它帮助人构建、测试和修改自动化系统；Jev也没有取代程序员，而是把某些已经形式化的语义判断变成可被软件直接消费的构件。

八、从Prompt到Program：自动化是一条成熟路径

许多团队的问题不是使用了错误模型，而是把仍处在探索阶段的提示词原型，直接推入了需要稳定契约的生产流程。协作与自动化之间需要一个逐步收敛的过程。

这条路径也为“人是否应该在环路中”提供了动态答案：在问题尚未被理解时，人必须深度参与；当任务被充分分解、错误可测、回退可靠以后，人可以退出每一次执行，只保留制度性控制；当环境变化时，人重新进入。

九、对AgentOS、开源与中国产业的启示

1. AgentOS不会只有一个万能模型

未来的AgentOS更可能是异构系统：生成模型负责理解开放意图、规划和创造；类型化决策模型承担高频判断；普通代码保证事务、权限和状态一致性；控制层根据成本、风险与置信度决定路由。真正的竞争焦点不是“支持哪个模型”，而是能否为不同任务选择正确的智能形态。

2. 开放接口需要从文本协议走向行为契约

今天的开源Agent生态重视工具调用、上下文和技能格式。下一步还需要开放概率语义、阈值策略、评测集、升级路径和审计事件。只有Schema没有校准，软件仍不知道何时可以信任结果；只有模型没有运行契约，自动化仍停留在演示。

3. 企业不应把Copilot和Automation放进同一个ROI口径

Copilot的价值可能体现为个人创造速度、员工体验和探索数量，难以只用替代工时衡量；Automation则必须计算直通率、人工升级率、误判损失、漂移和事故恢复。两者混在一起，前者会因为“不能完全无人”被低估，后者会因为“模型看起来很聪明”被过度授权。

4. 中国的模型、芯片和行业软件需要共同定义自动化原语

对中国开源大模型和Agent框架而言，机会不只是复刻一个更好用的Coding Agent，还包括面向制造、金融、医疗、政务和运营流程，建立可校准、可移植、可审计的决策原语。模型企业提供语义能力，芯片与推理平台提供低成本高并发，行业伙伴提供真实损失函数和评测，开源社区则让接口、基准与治理不被单一厂商封闭。

这也给国产AI芯片工具链提出更具体的要求：优化目标不能只有大模型吞吐，还要覆盖大量低延迟、小决策、并行调用和概率校准工作负载。Agent时代的算力需求，既包括长链推理，也包括嵌入软件深处、每秒发生无数次的微小语义判断。

结语：成熟的AI，知道人应该在哪里

DHH代表的是一个令人兴奋的现在：自然语言正在降低软件创造门槛，一个人可以调动多个Agent，把过去不会开始的想法迅速做出来。Almeida指向的是另一个尚未完成的未来：AI不只帮助人生产更多软件，还要成为软件内部可靠、廉价、可组合的判断能力。

前者让软件更容易被创造，后者让软件本身更聪明。前者需要保留模糊、试错和人的品味，后者需要压缩状态空间、暴露概率并建立契约。把其中任何一条路线宣布为唯一未来，都会漏掉另一半问题。

Agent时代真正的分界线，不是系统里有没有人，而是人以什么方式存在：是在每次执行中被迫兜底，还是在系统之外定义目标、风险和责任。

Claude Code之后，不会只有一个“更自主的Claude Code”，也不会所有任务都变成Choice、Score和Noul。更可能出现的是分层的软件新栈：人和生成式Agent共同探索，类型化模型与代码稳定执行，治理系统决定何时自动、何时升级、何时停止。

最成熟的AI系统，不是永远把人留在环路中，也不是急于拿掉人；而是知道人应该在哪里。
