Claude Code · Jev · Autonomous Software

Claude Code消失之后
AI向上成为Agent，还是向下成为软件原语？

从Boris Cherny与Diogo Almeida的两场访谈，看自主智能的两条路线

Boris希望有一天亲手删除Claude Code，让通用Agent跨越产品边界；Almeida认为Claude Code仍属于旧范式，要把智能压缩为软件可直接调用的类型化决策。两条路线并非简单替代，而是在从上层和底层同时重写软件。

深度解读与比较分析｜2026年9月

Claude Code创始人Boris Cherny在计算机历史博物馆的访谈中，给出了一个看似违反商业常识的愿望：他最期待的时刻，是团队能够亲手把Claude Code从代码库里删除。并不是因为产品失败，而是因为模型能力和交互方式继续演进以后，今天以终端为中心的独立产品形态可能不再必要。[1]

Jev创始人Diogo Almeida的判断更加尖锐。他认为Claude Code和ChatGPT仍属于同一个“辅助时代”：它们的核心仍是围绕一个在场的人工作。真正的下一站，应当是软件在后台独立、可靠地完成工作，而不是继续等待人类阅读、确认和兜底。[4]

两个人都在预言Claude Code会被超越，却把未来指向两个方向：一个让Agent获得更宽的行动空间、更长的时间跨度和更多工具；另一个主动收窄模型输出，把智能变成类似if、switch和sort的类型化原语。

一、两个判断为何听起来矛盾

Boris描述的Claude Code，已经远远超过“坐在程序员旁边补全代码”的工具。模型可以编辑文件、运行Bash、执行测试、观察错误，再决定下一步；主Agent还可以拉起多个子Agent，让不同模型并行分析日志、搜索代码和验证假设。

在他的设想中，Agent会进一步离开终端，进入Slack等协作环境，像团队成员一样理解讨论，主动接下任务，在数小时之后带着代码、分析和验证结果返回。编程、产品、研究与数据工作的边界随之变得模糊。Claude Code之所以可以被“删除”，是因为它的能力已经扩散到更大的通用协作界面中。

Almeida却把这种进展仍然归入“辅助”。在他看来，只要系统主要面向一个人输出文本、代码和解释，只要人仍然承担理解结果和决定后续动作的责任，它就没有跨过自主自动化的边界。Claude Code可以极大提高生产力，却不等于企业已经可以把一项业务流程交给软件后长期不再过问。

看似冲突的根源，是两人对“自主”使用了不同定义：

Boris所说的自主，是Agent能够独立完成更长的行动链；Almeida所说的自主，是业务流程能够不再依赖持续的人类监督。

二、Boris的路线：让Agent向外扩张

Claude Code的技术起点并不神秘：给大模型文件读写和终端工具，让它从“提出建议”变成“操作环境”。但这一小步改变了交互闭环。模型写下代码以后可以自己运行，失败以后可以读取报错并修复，不再需要人把内容在聊天框、编辑器和终端之间反复搬运。

Boris把早期困境概括为“模型悬置”：基础模型已经具备更强能力，产品界面却仍然按照旧能力设计，反而限制了模型。由此形成Claude Code的产品哲学：工具保持少而直接，给模型足够发挥空间，通过真实使用观察它怎样行动，再决定增加或删除什么。

能力来自行动闭环

读取环境、修改状态、执行测试和依据反馈继续行动，比单次生成一段代码更接近真实工程。

自主来自时间延长

任务从几分钟扩大到数小时，Agent能够推翻假设、拉起子Agent并整合结果。

边界来自环境约束

沙箱、文件系统权限、网络出口和独立审查模型定义Agent能够触及的最大范围。

人的价值向上迁移

代码实现不断自动化以后，问题选择、跨领域理解、综合判断和责任担当更加稀缺。

这条路线的终点不是更复杂的命令行，而是产品边界逐渐消失。Agent进入团队沟通、数据系统和业务工具以后，用户不再需要思考“现在是否打开Claude Code”，而是在原有工作场景中直接委托任务。

因此，“删除Claude Code”并不是删除Agent，而是让Agent从一个垂直工具变成更普遍的工作层。

三、Almeida的路线：让智能向软件内部下沉

Almeida从另一个问题出发：为什么大模型已经能解决很难的数学和代码问题，企业处理退款、邮件路由、风险分类等看似简单的工作时，仍然不敢把人拿掉？

他的回答是，当前大模型首先被训练成面向人的助手。模型输出开放文本，优化目标强调有用、自然和符合人类偏好。这非常适合对话和协作，却不天然等于一个可以嵌进程序、长期稳定运行的决策构件。

Jev因此放弃开放式字符串生成，提供Choice、Score与Noul三类类型化决策：从预设选项中选择、按照量表评分，或给出某个命题为真的概率。程序不需要解析模型写出的JSON或自然语言，而是直接获得受Schema限制的值和置信信息。[5]

这条路线的关键不在于再造一个更会聊天的小模型，而是改变软件可以使用的智能接口。Almeida把它称为“System One Model”：输入非结构化状态和类型化问题，输出程序可直接消费的概率决策。[6]

它追求的不是一次完成复杂开放任务，而是让海量、重复、过去只能由人理解的微小判断，以低延迟和可度量置信度进入普通软件。

四、真正的分歧：通用智能能否靠工程护栏进入生产

两位创始人的共同点其实很多。他们都不满足于在旧软件旁边增加聊天框，都认为逐次人工确认无法支撑真正规模化的Agent，也都在寻找一种让AI进入生产系统而不需要人持续点击的方法。

真正的分歧在更深处：通用生成模型的自由度，能否通过Harness、沙箱、分类器和权限系统得到充分治理；还是必须从训练目标和输出形态开始改变。

比较维度Claude Code路线Jev路线
核心对象通用、长链、可使用工具的Agent专门、快速、类型化的语义决策模型
自主性的来源更多工具、更长上下文、记忆、子Agent与环境权限更小决策单元、预定义类型、校准概率与代码组合
输出空间开放：文本、代码、命令和行动序列封闭：Choice、Score、Noul等预设结构
主要优势通用、灵活，能处理未知步骤和开放目标低延迟、可组合，格式错误空间被直接消除
主要风险行动漂移、提示词注入、奖励作弊与越权操作类型正确但判断错误、概率失准与数据漂移
安全机制沙箱、网络与文件边界、审查模型、审计和回滚类型契约、概率阈值、人工升级和持续校准
更适合开发、研究、排障、跨工具任务和低频复杂工作分类、路由、筛选、评分和高频稳定流程

Boris愿意让模型保持较大的自由度，再从外部限制它能造成的影响；Almeida选择先减少模型能够表达和执行的状态，再让普通程序掌握最终组合逻辑。一个主要治理“行动边界”，另一个主要治理“决策边界”。

五、两种安全观：替代疲劳的人，还是减少不确定的模型

Boris对传统Human-in-the-loop提出了一个非常现实的批评：如果用户每天面对大量权限弹窗，确认动作会逐渐退化为条件反射。Anthropic在其公开的Auto Mode材料中报告，相关使用情境下用户批准了约93%的Claude Code权限请求；这一观察并不代表所有产品或场景，却提示批准疲劳可能让“有人确认”在形式上存在，在实质上失效。[2]

Claude Code Auto Mode的回答，是让独立分类器替代部分人工批准。系统先用规则放行只读工具和项目内可审查修改，再把Shell、外部网络、跨目录操作等潜在高风险行为交给独立上下文中的模型判断；同时以文件系统、网络隔离和沙箱限制最坏影响。Anthropic也明确承认，任何概率防御都存在非零漏报率，因此不能只依赖分类器。[2][3]

Almeida对这一方案可能提出更根本的追问：如果执行者和审查者都来自以人类偏好为中心的通用语言模型，系统是否只是在用另一个概率模型监督概率模型？他的答案是改变模型训练目标，让系统输出经过校准的概率，并把最终动作交回类型和代码。

两种方法并非互斥。即便模型只输出有限选项，高风险业务仍需要权限、审计与回滚；即便通用Agent被关在沙箱里，其内部用于放行、路由和风险判断的环节，也可以使用类型化概率模型。

六、两条路线各自没有解决什么

Claude Code式Agent：长链自主会累积误差

工具越多、运行越久、子Agent越多，系统接触的不可信输入和外部状态也越多。一次微小误解可能在几十个步骤后变成真实操作。沙箱能够限制物理范围，却不能保证Agent正在解决正确的问题；独立分类器可以拦截明显危险行为，也很难判断一项看似正常的修改是否偏离了产品目标。

“无需逐次确认”不等于“无需责任人”。更合理的变化，是从每一步点击批准，转向事前设定边界、运行中观察偏差、关键节点升级以及事后可追溯。

Jev式模型：类型安全不等于语义正确

如果接口只允许返回A、B、C，接口设计可以避免模式之外的字符串；但模型仍然可能在三个合法选项中选错。总体置信度得到校准，也不意味着每个样本都安全。一个标注为80%置信度的批次如果长期有约80%正确，仍然意味着其中约五分之一可能错误。

TypeSafe公布的速度和成本优势来自公司自己的工作流评测。其官方博客同时说明，193.6倍和444.6倍属于实际收益的高端区间，评测任务、参考模型和服务位置也会影响结果。它们足以证明方向值得测试，却还不能证明所有业务都应从通用模型迁移。[6]

需要避免的两个误读：Claude Code的自主性不等于可以无限授权；Jev所说的“不会幻觉”主要指不会产生类型或Schema之外的输出，不等于永远不会作出错误判断。

七、可能的答案：上层Agent，下层原语，中间是治理

如果把两条路线放进同一套系统，它们并不争夺完全相同的位置。通用Agent更像动态的规划与创造层，类型化模型更像稳定的判断与执行层，控制平面则决定两者可以使用什么数据、工具和权限。

例如，一个企业Agent可以接受“分析过去一个月客户流失并提出干预方案”的开放目标。它使用通用模型规划分析、查询数据和生成假设；在处理数百万封邮件时，调用类型化模型判断取消意图、情绪和风险；最终由确定性业务系统按照金额、客户等级和权限执行动作。高风险样本升级给人，所有步骤留下审计记录。

这套架构中，Boris和Almeida的路线不是谁淘汰谁，而是分别处理不同粒度的不确定性。

八、真正会消失的，也许是“AI产品”这个独立类别

Boris希望删除Claude Code，因为Agent能力最终会进入所有协作界面，不再需要用户主动打开一个专门的编程工具。Almeida认为下一时代不属于Claude Code，因为智能会进入软件内部，用户甚至意识不到某次路由、排序或筛选由模型完成。

两种未来都指向“界面消失”。一个消失在更大的Agent之中，另一个消失在更小的软件原语之中。前者像操作系统或团队成员，后者像数据库查询、规则引擎或一条智能if语句。

Claude Code真正的成功，可能不是永远保留这个名字，而是让“软件会自己工作”变成默认能力。

九、对AgentOS、开源生态和中国产业的启示

1. 不要把Agent路线简化成“大模型再加几个工具”

通用Agent需要Harness、记忆、子Agent、沙箱、身份、权限和可观察性；类型化自动化需要Schema、概率语义、校准、阈值和漂移监控。未来AgentOS的核心，不只是把工具接给模型，而是把多种智能接口放进统一的控制平面。

2. 开源竞争会同时发生在上层协议和底层原语

上层需要开放工具协议、技能格式、任务状态、Agent间通信和审计事件；下层需要开放类型化决策接口、置信度表达、评测集和跨模型校准方法。只开放模型权重，不能自动形成可靠的软件生态。

3. 企业应把两类ROI分开

通用Agent的价值主要体现在研发周期、探索数量、跨部门协作和复杂任务完成率；类型化模型的价值更适合用调用成本、直通率、误判损失、升级率和延迟衡量。用“替代了多少人”同时评价两者，会让创造工具被低估，也会让自动化系统被过度授权。

4. 国产模型、芯片与行业软件需要形成异构智能栈

中国企业的机会不只是在通用Coding Agent上追赶，还可以围绕制造、运营及其他已具备清晰数据边界和审计要求的行业流程，开发低延迟、可校准、可审计的行业决策模型。模型企业提供语义能力，芯片和推理平台优化长链推理与高频微决策两种负载，行业伙伴在依法合规、数据安全和最小必要原则下提供可验证的业务约束，开源组织推动接口、评测和治理保持可迁移。

对于AI芯片，这意味着性能评估不能只有长上下文和大模型Token吞吐，还要关注并行的小问题、极低延迟、稳定概率输出以及大规模在线校准。Agent时代的智能消费，既可能是一项运行十二小时的复杂任务，也可能是每秒发生百万次、每次只返回一个选择的微小判断。

结语：两种自主，正在共同定义软件的下一站

Boris看到的是通用模型能力继续增长以后，产品壳层不断被突破：从终端到团队协作，从单个Agent到数字团队，从写代码到完成更完整的工作。Almeida看到的是另一种尚未释放的价值：智能不应永远以对话和长文本出现，它应当成为普通软件能够稳定依赖的基础构件。

一个扩大自由度，一个约束自由度；一个让Agent承担更大的任务，一个把任务拆成更小的决定；一个相信通用模型加工程护栏可以不断走向自主，一个认为真正自动化要求新的训练目标和输出接口。

这确实是一场技术路线之争，但不是只能留下一个答案的零和竞争。现实系统既需要面对未知的通用Agent，也需要处理已知的类型化智能；既需要模型大胆探索，也需要软件保守执行。

Claude Code消失之后，AI可能同时向两个方向进入软件：向上成为能够承担工作的Agent，向下成为软件可以直接依赖的原语。

最终决定哪条路线成立的，不是演讲里的口号，而是三件事：它是否真正完成了工作，失败是否被限制在可承受范围内，以及人在离开每一次操作之后，是否仍然掌握目标、规则和责任。
