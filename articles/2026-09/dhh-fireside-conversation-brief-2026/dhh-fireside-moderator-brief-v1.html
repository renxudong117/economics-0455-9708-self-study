Moderator brief · 60–90 minutes · v1

从 “Pencils Down” 到
“可塑的机器”

与 DHH 的炉边谈话：不把他问成“AI 观点代言人”，而是追问一位长期做软件的人，如何在 Agent 时代重新理解创造、架构、所有权与共同体。

主持人工作稿｜问题以中文写出，并配可直接使用的英文问法；可按现场回应自由删减与重排。

这不是一场“AI 会不会取代程序员”的辩论。更有意思的主线是：DHH 在很短时间内从谨慎地谈受监督协作，走到把手写代码称作例外；与此同时，他仍然反复强调架构、品味、运行速度、用户对机器的控制权，以及维护者的最终判断。谈话应让听众看见这条变化背后的工作方法，而不是把几句锋利口号剪成结论。

建议的主命题：当 Agent 可以实现更多，软件的稀缺资源并没有消失，而是从“写出实现”转向“提出值得做的事、维持系统的内在一致、建立可信的反馈，以及让人仍能拥有并塑造自己的计算环境”。

一、时间安排：75 分钟为主，90 分钟可展开

0–7 min
开场：“过去一年，你似乎不是换了一个工具，而是换了一种与电脑相处的方式。”用一个具体变化入场。
7–20 min
从怀疑到投入：Agent 带来了什么；最初的失败如何改变了方法。
20–36 min
工程的重新分工：Pencils Down、架构、验证、品味与责任。
36–48 min
Rails、Rust 与约定：不做“哪一个取代哪一个”的假二选一，谈如何重新估算架构成本。
48–60 min
Omarchy 与可塑的机器：默认答案、用户所有权、Agent 可访问性。
60–72 min
开源共同体：Agent 贡献如何提升，而非稀释，维护者判断如何留下。
72–82 min
全球视角：面向不同语言、模型和开发者群体，什么才是有吸引力的开放协作。
82–90 min
收束：留给下一代开发者的一条实践建议，以及他还想亲手看见的未来。

60 分钟压缩版：保留第 1、3、5、7、9、11、13、15、17 题；每题只追问一次。90 分钟版：每段多保留一个追问，并让观众在“开源共同体”之后参与 8–10 分钟问答。

二、核心问题卡

共 17 题。不是题库竞赛；现场通常只需要 11–13 题。标注 必问 的题构成完整 60 分钟主线。

01 · 开场必问

过去一年，是什么让你不再只是“试用 AI”，而是开始改变自己的工作方式？

“Over the last year, what made you move from merely trying AI to changing how you actually work with computers?”

用“变化”而非“立场”开场，给他机会讲真实经历，而不是重演争论。

追问：有没有一个原本不会开始的项目，突然变得值得做了？
02 · 愉悦

你写过“endless execution”：每个想法都仿佛更接近可执行。这个状态带给你的，除了速度，还有什么？

“You wrote about ‘endless execution’. Beyond speed, what has that state changed in the way you imagine and choose ideas?”

把“效率”转回创造欲与取舍；这会让对话有温度，但不走向泛泛的哲学。

03 · 失败必问

你谈过早期让更多人用 Agent 提交改动，结果架构反而失去一致性。后来真正改变了什么：模型、工具链、代码库规则，还是你自己的介入方式？

“You’ve described early agent-assisted contributions that made the architecture less coherent. What actually changed afterwards: the models, the harness, the repository rules, or your own role?”

先让他讲失败，之后再谈 Pencils Down 才不显得口号化。

04 · 边界

你如何区分“vibe coding”与真正的 agentic engineering？如果一个团队自称在用 Agent，你最想先看它的哪三件事？

“How do you distinguish vibe coding from agentic engineering? If a team says it is agentic, what are the first three things you would inspect?”

把抽象概念压到可观察的工程能力：任务边界、反馈/测试、审查和部署责任。

05 · Pencils Down必问

“手写代码成为例外”最容易被误解。对你而言，它究竟是一个组织原则、一个个人习惯，还是一种用来发现工作流缺陷的报警器？

“‘Handwritten code is the exception’ is easy to misunderstand. For you, is it an organizational principle, a personal habit, or an alarm that reveals a broken workflow?”

请他定义这句话，而不是主持人替他定义。避免落入“人还要不要写代码”的二元问题。

追问：在什么情况下，你仍然会主动亲手写，或要求人亲手写？
06 · 人的工作

当实现越来越便宜，人的瓶颈是否变成了判断、品味和沟通？这些能力如何被训练，而不只是被赞美？

“As implementation gets cheaper, do judgment, taste, and communication become the bottlenecks? How can teams train these skills, rather than merely praise them?”

这会把“人留在环里”落到组织实践，而非职业焦虑。

07 · Rails必问

你把 Rails 的 Convention over Configuration 重新解释为 Token 效率。请给一个非 Rails 开发者也能理解的例子：什么样的“约定”，会让人和 Agent 都少走弯路？

“You’ve reframed Convention over Configuration as token efficiency. Can you give a non-Rails example of a convention that helps both people and agents waste less context?”

把 Rails 的历史哲学讲成所有工程团队都能带走的方法。

08 · 架构

HEY 的原生客户端与 Rust 后端，是一次很强烈的架构选择。我们不把它理解成“Rails 被 Rust 取代”；它真正说明了哪些成本，正在被 Agent 重新定价？

“Without turning this into ‘Rust replaces Rails’, what costs are agents repricing in an architectural decision like the new HEY stack?”

用“重新定价”替代“取代”，既准确也能引出性能、部署、体验与团队成本。

追问：什么情况下，Web + Rails 仍然是最好的答案？
09 · 速度必问

你一直在意启动时间、响应和小团队的速度。今天的 Agent 会不会让我们更容易造出“更多但更重”的软件？怎样让生成能力反过来帮助我们做出更轻、更快、更可维护的系统？

“Could agents make it easier to produce more—but heavier—software? How do we use generative capacity to make systems lighter, faster, and more maintainable instead?”

这是对“AI 代码优先”最友善也最必要的压力测试。

10 · 所有权

你用“可塑的机器”描述 Omarchy：用户可以先获得一套完整答案，再把它改成自己的。omakase 的默认主见，与用户真正拥有机器之间，怎样保持张力而不冲突？

“Omarchy starts with an opinionated default, then invites people to make it their own. How do you hold that tension between a strong default and genuine ownership?”

这让“拥有计算机”不止停留在开源许可证，而进入产品设计与迁移自由。

11 · Agent 可访问性必问

Basecamp 正在变得 agent-accessible：API、CLI、Skills 都是产品的一部分。未来产品应让 Agent 更像人一样使用现有环境，还是应当为 Agent 重画接口和权限边界？

“As products become agent-accessible through APIs, CLIs, and skills, should agents adapt to human environments, or should we redesign interfaces and permission boundaries for agents?”

从开发工具进入真实业务软件，也自然带出权限、审计、用户授权与可信执行。

12 · 安全

当 Agent 可以持续运行、拥有记忆并代表用户行动时，怎样让“给它更多能力”不演变为“交出无法收回的权限”？

“When agents can persist, remember, and act for users, how do we expand capability without handing over permissions we cannot take back?”

这是高质量听众会关心的现实问题。问原则与产品设计，不要求他给出危险的操作细节。

13 · 开源必问

Agent 可以筛选、测试、总结 Pull Request，但最终“该往哪里去”仍需要人决定。什么样的开源项目会因 Agent 贡献而更有生命力，而不是被低成本改动淹没？

“Agents can triage, test, and summarize pull requests, but humans still decide where a project goes. What makes an open-source project more alive with agents rather than drowned by cheap changes?”

回到维护者、贡献者与治理的核心；对全球开源社区都具有共鸣。

14 · 文化

Omarchy 既谈工程，也谈美、玩心和共同体。你认为这种“喜欢电脑本身”的情感，在今天仍然是严肃技术项目的竞争力吗？

“Omarchy makes room for beauty, play, and community. Is a love of computers itself still a competitive advantage for serious technical projects?”

让他谈文化而不必落入意识形态或围绕争议表述打转。

15 · 全球协作必问

你同时使用不同国家、不同开放程度的模型与工具。对一个想真正走向全球的开源项目而言，除了英文文档与 GitHub，它还要提供什么，才能让不同地区的开发者成为共同作者？

“You work with models and tools from many places. For an open-source project that wants to become genuinely global, what must it offer beyond English documentation and a GitHub repository?”

从中国及全球开发者的现实出发，但不把嘉宾推到地缘政治表态中。

16 · 给团队

如果你今天面对一支很小、资源有限、但希望把 Agent 与开源做好的一线团队，你会让他们先少做什么，又先建立什么？

“If you were advising a small, resource-constrained team trying to do agents and open source well, what would you tell them to stop doing first—and what would you have them build first?”

为企业、创业者和开发者听众留下一条直接可用的建议。

17 · 收束必问

请完成这句话：在 Agent 时代，计算机真正重新属于我们，不是当它替我们做得更多，而是当它……

“Finish this sentence: In the age of agents, a computer truly belongs to us not when it does more for us, but when it…”

一句有记忆点的结尾。若他不喜欢填空，可替换为：“你希望三年后人们仍然记得什么？”

三、主持人的转场句

把口号拉回现实

“I don’t want to turn that into a slogan. Can we make it concrete?”

适用于 Pencils Down、AI 生产力、开源与“拥有计算机”等大词之后。

不制造假对立

“Let me put that without forcing a false choice…”

适用于 Rails / Rust、Web / Native、用户便利 / 用户控制等话题。

把判断问成方法

“What would that look like on a normal Tuesday for a small team?”

把宏观判断落回团队、代码库、产品路线和反馈机制。

友善地压力测试

“What is the strongest counterargument to your own excitement?”

比“你是否太乐观”更开放，也更容易得到有分寸的回答。

四、现场边界与准备清单

不要做：把访谈变成对其政治、网络争议、竞争者或未经核验指标的追问；把 HEY 的技术选择称为“抛弃 Rails”；把他在演讲中的估算数字当作独立性能结论。若嘉宾自行延展到争议话题，可礼貌回到“这如何影响你设计产品、社区或计算机”的主线。
  • 会前请他确认：是否允许谈 HEY 架构、Omarchy 路线、Basecamp agent-accessible 的后续，以及哪些仍属未公开产品计划。
  • 准备一个屏幕画面即可：展示“变化 → 工程 → 框架 → 机器 → 社区”的路线图；不要投放大段引语或技术参数。
  • 听众提问筛选：优先收集“真实工作流、开源协作、产品/系统设计”的问题，避免要求预测模型排名、商业数字或争议立场。
  • 记住对谈的节奏：每 8–12 分钟让他讲一个具体项目、一个判断或一次反转；不要连续三题都停留在理念层。

五、主持人的一段开场（可直接使用）

“很多人认识你，是因为 Rails、Basecamp，或你对小团队和好工具的长期坚持。但过去这一年，你似乎重新找回了一种更直接的兴奋：不是让 AI 替人宣布终局，而是让更多想法能够更快地成为可以被使用、被批评、被改造的软件。今天我们想从这条变化谈起：当 Agent 开始承担实现工作，人应该把自己放在哪里？而我们又如何保有对机器、代码与共同体的主见？”
